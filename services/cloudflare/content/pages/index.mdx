## Build output and request execution are different layers

A Pages build produces deployable assets. A visitor can receive a static file or
reach a Pages Function for dynamic behavior. Functions use the Workers runtime;
build processes and browser JavaScript do not share their isolate or globals.
[Pages Functions](https://developers.cloudflare.com/pages/functions/).

## Pages Functions: a Pages API on the Workers runtime

Functions are server-side code deployed with your Pages application. In the
usual mode, Pages supplies file-based routing and a handler API:
`functions/api/hello.js` handles `/api/hello`, exporting `onRequest(context)`
or a method-specific handler such as `onRequestGet(context)`.
[File routing](https://developers.cloudflare.com/pages/functions/routing/).

The context contains `request`, `env`, route `params`, and `waitUntil()`.
Resource bindings are available through `context.env`.
`context.next()` continues through middleware or falls back to asset serving.
You still use familiar runtime APIs such as `Request`, `Response`, and outbound
`fetch()`, but the entry-point signature differs from a standalone Worker’s
`fetch(request, env, ctx)`.
[Functions API](https://developers.cloudflare.com/pages/functions/api-reference/).

**Advanced mode uses Worker module syntax.** Put `_worker.js` in the build output
and export a Worker-style fetch handler. This replaces the `/functions` router
and middleware; your code handles routing and serves static assets through
`env.ASSETS.fetch(request)`. It is still deployed as part of the Pages project.
[Advanced mode](https://developers.cloudflare.com/pages/functions/advanced-mode/).

So a normal Pages Function is not just a route pointing at a separately
deployed Worker. It has a Pages authoring API on the same execution runtime;
its usage counts toward Workers quotas. Calling a separate Worker through a
service binding is another, explicit integration.
[Bindings](https://developers.cloudflare.com/pages/functions/bindings/),
[Limits](https://developers.cloudflare.com/pages/platform/limits/).

The diagram above shows the file-based mode. Invocation is also controlled by
`_routes.json`: excluding static paths avoids invoking Functions for them.
A route falling back to an asset is not itself proof that no Function ran.
[Invocation routes](https://developers.cloudflare.com/pages/functions/routing/#functions-invocation-routes).

For server-side state, concurrency, Wasm, and fetch/cache APIs, use the
[Workers runtime model](/cloudflare/workers/#architecture). A binding in a
Function reaches an external resource; it does not bundle that resource into
the deployed assets. [Function bindings](https://developers.cloudflare.com/pages/functions/bindings/).

<h2 id="api-example">API example</h2>

Pages Functions uses `onRequestGet(context)` instead of a Worker’s fetch
handler. Save this as `functions/api/hello.js` in a Pages project; GET
`/api/hello?name=Sam` returns a JSON greeting. No resource binding is needed.

```javascript
export const onRequestGet = ({ request }) => {
  const name = new URL(request.url).searchParams.get('name') ?? 'world';
  return Response.json({ greeting: `Hello, ${name}!` });
};
```

To use storage from this Function, configure a Pages binding and access it via
`context.env`. A separate Worker can call the deployed Pages URL with `fetch()`;
Pages does not provide a Pages-specific storage binding for that call.

[Pages Functions API](https://developers.cloudflare.com/pages/functions/api-reference/),
[Pages resource bindings](https://developers.cloudflare.com/pages/functions/bindings/).

<h2 id="latency">Latency</h2>

**Separate static asset delivery from Functions execution.** Pages serves
uploaded static assets through Tiered Cache. A nearby cache hit and a request
that must fill a cache have different paths; asset size and the client network
also affect completion time. The serving guide does not publish a general TTFB
(time to first byte) range. [Serving and caching Pages](https://developers.cloudflare.com/pages/configuration/serving-pages/).

For dynamic routes, use the [Workers latency model](/cloudflare/workers/#latency)
and include the Function’s downstream calls. Our measurement guidance: compare
static and dynamic routes separately, recording TTFB and full download time for
representative asset sizes and user locations. Build/deployment duration is a
separate metric from serving latency.

## Deployment

Choose Git integration for Cloudflare-managed builds, or build the assets
yourself and upload with `npx wrangler pages deploy <OUTPUT_DIR>`. Functions are
part of the application deployment; configure their resource bindings as well.
[Git integration](https://developers.cloudflare.com/pages/get-started/git-integration/),
[Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/).

For the CLI’s local wrapper, `npx wrangler pages dev <OUTPUT_DIR>` serves the
built files and runs Functions. Build first. Local Pages D1 bindings cannot
point at a remote database.
[Local development](https://developers.cloudflare.com/pages/functions/local-development/).
