## Supported, no longer recommended

The Pages overview opens by recommending Workers, which it calls Cloudflare’s
primary platform for building applications. There is no deprecation notice or
sunset date, and the docs are still maintained. Existing projects keep working.
[Pages overview](https://developers.cloudflare.com/pages/).

**The one thing only Pages does:** custom domains on zones whose nameservers are
not managed by Cloudflare. Four more Pages features need a workaround on Workers
today: Early Hints, branch deploy controls, file-based routing for Functions, and
Pages Plugins. Everything else, including Durable Objects and Cron Triggers, is
available only on Workers or works the same on both.
[Compatibility matrix](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/#compatibility-matrix).

Our guidance: start new work on [Workers static assets](/cloudflare/workers/#static-assets).
Stay on Pages when you rely on an external-nameserver domain or its branch
controls, and plan the migration below otherwise.

## Functions use a Pages-specific handler API

Pages Functions are server-side code deployed with the site. In the usual mode,
Pages supplies file-based routing: `functions/api/hello.js` handles `/api/hello`
and exports `onRequest(context)` or a method-specific handler such as
`onRequestGet(context)`. The context carries `request`, `env` (resource
bindings), route `params`, `waitUntil()`, and `next()`, which continues through
middleware or falls back to asset serving. This is the same Workers runtime with a
different entry-point signature from a Worker’s `fetch(request, env, ctx)`.
Invocation is controlled by `_routes.json`, so excluding static paths keeps
Functions from running for them.
[Functions API](https://developers.cloudflare.com/pages/functions/api-reference/),
[File routing and invocation routes](https://developers.cloudflare.com/pages/functions/routing/).

**Advanced mode** replaces the router with a `_worker.js` module in the build
output that exports a Worker-style fetch handler and serves files through
`env.ASSETS.fetch(request)`. That is the same shape as a Worker with static
assets, which is why such projects migrate easily.
[Advanced mode](https://developers.cloudflare.com/pages/functions/advanced-mode/).

Functions usage counts toward Workers quotas, on the Workers plan rather than the
zone plan. For server-side state, concurrency, and fetch/cache behavior, use the
[Workers runtime model](/cloudflare/workers/#architecture).
[Bindings](https://developers.cloudflare.com/pages/functions/bindings/),
[Limits](https://developers.cloudflare.com/pages/platform/limits/).

<h2 id="api-example">API example</h2>

Save this as `functions/api/hello.js` in a Pages project; GET
`/api/hello?name=Sam` returns a JSON greeting. No resource binding is needed.

```javascript
export const onRequestGet = ({ request }) => {
  const name = new URL(request.url).searchParams.get('name') ?? 'world';
  return Response.json({ greeting: `Hello, ${name}!` });
};
```

To use storage, configure a Pages binding and read it from `context.env`.
[Pages Functions API](https://developers.cloudflare.com/pages/functions/api-reference/),
[Pages resource bindings](https://developers.cloudflare.com/pages/functions/bindings/).

## Migrating to Workers

The migration guide covers the common steps; most are configuration:

- **Output directory:** `pages_build_output_dir` becomes `assets.directory` in
  a Wrangler file that also sets `name` and `compatibility_date`.
- **Serving behavior is explicit:** Pages guessed SPA versus 404 handling from
  the presence of `index.html` and `404.html`; Workers requires
  `not_found_handling` to be set.
- **Functions:** a framework adapter targets Workers directly; an advanced-mode
  `_worker.js` becomes the Worker’s `main` (kept out of the upload with
  `.assetsignore`); a `functions/` folder is compiled into one Worker script
  with `wrangler pages functions build --outdir`, which remains available.
- **Domains:** custom domains and routes work when the zone is on Cloudflare
  nameservers. When traffic has moved, delete the Pages project.

[Migrate from Pages to Workers](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/).

<h2 id="latency">Latency</h2>

Static assets are served through Tiered Cache, so a nearby cache hit and a
cache fill have different paths; the serving guide publishes no general TTFB
(time to first byte) range. Dynamic routes follow the
[Workers latency model](/cloudflare/workers/#latency) plus the Function’s
downstream calls. Measure static and dynamic routes separately, and treat
build duration as a separate metric from serving latency.
[Serving and caching Pages](https://developers.cloudflare.com/pages/configuration/serving-pages/).

## Deployment

Choose Git integration for Cloudflare-managed builds, or build the assets
yourself and upload with `npx wrangler pages deploy <OUTPUT_DIR>`. Functions
deploy with the site; configure their bindings as well.
[Git integration](https://developers.cloudflare.com/pages/get-started/git-integration/),
[Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/).

For the CLI’s local wrapper, `npx wrangler pages dev <OUTPUT_DIR>` serves the
built files and runs Functions. Build first. Local Pages D1 bindings cannot
point at a remote database.
[Local development](https://developers.cloudflare.com/pages/functions/local-development/).
