## A small stateful service for each thing in your app

Think **a Worker-style instance specific to each Durable Object, with its own
memory and private database**. Its code runs on the Workers runtime; the object
identity lets callers address that particular stateful instance. Callers using the same identity in a namespace reach the same
object. You choose what that identity represents: a cache partition, counter,
topic, tenant, document, game session, or chat room.

Some useful patterns you can build with this primitive:

- **A coherent cache:** keep shared values in one object's memory, with reads and
  updates handled by its code. This can serve a Memcached-style role; it is not
  a drop-in Memcached server. Memory can be lost on eviction, and callers still
  pay the network round trip to the object's location.
- **Shared counters and per-tenant coordination:** send operations for one
  identity to the same code and state, persisting values that must survive.
- **An event bus (pub/sub broker):** use an object per topic or partition to
  track subscribers and fan published events out over WebSockets. Your code
  implements the broker, including persistence and replay if subscribers need
  to catch up after disconnecting.
  [WebSocket coordination and fan-out](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).
- **Aggregation:** collect updates in memory and periodically persist a batch.
- **Collaborative applications:** coordinate document edits, game state, or chat
  participants. These are examples of the primitive, not a special object type.

The diagram shows the common architecture behind these patterns. Separate
identities give you independent objects; a single identity is not copied into
an independent active instance at every edge location.
[Durable Objects concepts](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/),
[Cloudflare’s design guidance](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/).
See [Latency](#latency) for the distinction between local state access and the
caller-to-object trip.

## Object identity survives; the active instance can change

An object’s durable storage and its current in-memory state have different
lifetimes. Eviction discards memory; a later activation reconstructs an instance
that can read its stored data. Put persistent application data in storage and treat active
connections or temporary calculations as lifecycle-dependent.
[Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/).

Use the [Workers page](/cloudflare/workers/#runtime-concurrency) for the base
single-threaded execution model, but do not transfer stateless Worker routing
assumptions to a named Durable Object. Identity is the reason callers can meet
at the same stateful unit.

<h2 id="api-example">API example</h2>

Configure `COUNTERS` as a binding to the exported `Counter` class with
SQLite-backed storage. Put both exports in `src/index.js`.
Each POST increments the same named object’s persistent counter.

**wrangler.jsonc — relevant configuration**

Merge this into your existing Worker configuration.
`COUNTERS` becomes `env.COUNTERS`; `Counter` matches the class exported below.
The `exports` declaration registers the class with SQLite storage.
[Configuration reference](https://developers.cloudflare.com/durable-objects/get-started/).

```json
{
  "durable_objects": {
    "bindings": [
      {
        "name": "COUNTERS",
        "class_name": "Counter"
      }
    ]
  },
  "exports": {
    "Counter": {
      "type": "durable-object",
      "storage": "sqlite"
    }
  }
}
```

**src/index.js**

```javascript
import { DurableObject } from 'cloudflare:workers';
export class Counter extends DurableObject {
  increment() {
    const sql = this.ctx.storage.sql;
    sql.exec(`CREATE TABLE IF NOT EXISTS counter (
      id INTEGER PRIMARY KEY, value INTEGER NOT NULL
    )`);
    return sql
      .exec(
        `
      INSERT INTO counter (id, value) VALUES (1, 1)
      ON CONFLICT(id) DO UPDATE SET value = value + 1
      RETURNING value
    `,
      )
      .one().value;
  }
}
export default {
  async fetch(request, env) {
    if (request.method !== 'POST') {
      return new Response('Use POST', {
        status: 405,
        headers: { Allow: 'POST' },
      });
    }
    const counter = env.COUNTERS.getByName('demo-counter');
    return Response.json({ value: await counter.increment() });
  },
};
```

Every caller using `demo-counter` in this namespace reaches the same global
singleton. A different name selects a different object. The increment happens
inside one SQL statement, rather than a caller reading and writing shared state.

[Calling a Durable Object](https://developers.cloudflare.com/durable-objects/get-started/),
[Durable Object SQL API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).

<h2 id="latency">Latency</h2>

**Local SQL queries can complete in microseconds.** Cloudflare’s September 2024
SQLite-in-Durable-Objects explanation describes same-thread database execution
with no network hop between your object code and SQLite. This is an internal
query timescale, not a bound on a Worker’s RPC call. Write responses can also
wait for durable confirmation through the runtime’s output gates.
[SQLite execution and write confirmation](https://blog.cloudflare.com/sqlite-in-durable-objects/).

**A globally addressable object still lives at a particular location.** Caller
distance adds a network round trip; the location guide does not give a universal
RPC latency range. A singleton is therefore coherent shared state, not a local
copy at every edge. [Placement and latency](https://developers.cloudflare.com/durable-objects/reference/data-location/).

Our measurement guidance: compare calls from nearby and distant Workers, reads
and persisted writes, and active versus newly activated objects. Include waiting
under load in the caller’s elapsed time, not just time spent inside a method.

<section slot="deployment">

## Deployment

Export the Durable Object class, configure its namespace binding and class
lifecycle declaration, then deploy the owning Worker with Wrangler. Follow the
current configuration guide when adding or changing classes; these changes
are distinct from editing the data inside existing objects.
[Durable Object setup](https://developers.cloudflare.com/durable-objects/get-started/),
[Class lifecycle configuration](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/).

`npx wrangler dev` wraps local execution. Initialize test state by calling object
methods rather than expecting a generic database-seeding command.
[Local object data](https://developers.cloudflare.com/workers/local-development/local-data/).
